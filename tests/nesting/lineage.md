# T001 — Linaje de entrega de `DD_OTR`

Fecha: 2026-09-21. Alcance: lectura estática del plugin en `feature/dd-product-nesting`; no se consultó una base de datos ni se asumió que un pedido equivale a una entrega física.

## Contrato de identidad para el adaptador futuro

Las OTR creadas por `createOTR` reciben `OrderType` y una referencia de línea de origen entre `C_OrderLine_ID`, `DD_OrderLine_ID`, `M_InOutLine_ID` y `M_MovementLine_ID`: la consulta pone las otras tres en cero y las copia a `DD_OTR`; el modelo generado expone las cuatro y `OrderType` ([createOTR.java:147](../../src/org/idempiere/tms/process/createOTR.java#L147), [createOTR.java:347](../../src/org/idempiere/tms/process/createOTR.java#L347), [I_DD_OTR.java](../../src/org/idempiere/tms/model/I_DD_OTR.java)). Como pueden existir OTR de otros orígenes o editadas, el adaptador deberá verificar exactamente una referencia positiva, el tipo, el `AD_Client_ID` de OTR y origen antes de resolver el alcance. `DD_OTR_ID`, cliente, producto, clasificación, ubicación y fecha prometida no son por sí mismos una identidad de entrega.

Para `MMS`/`MMR`, la clave identifica un documento de envío o recibo, no prueba que ya se ejecutó: la selección admite estados `DR`, `IP`, `CO` y `CL` ([createOTR.java:191](../../src/org/idempiere/tms/process/createOTR.java#L191)). Tampoco prueba por sí sola ruta, fecha de carga, vehículo candidato, compatibilidad de productos ni cabida. Esos portadores siguen siendo obligatorios según el plan. Si el origen no se encuentra, hay varias referencias positivas, el tipo no corresponde a la dirección, los clientes difieren o la relación no es única, el resultado también es indeterminado. Ningún caso usa `C_BPartner_ID` o `Classification` para completar una entrega faltante.

## Efecto sobre el flujo actual

`createFreightUnit` selecciona OTR por cliente y fecha o selección, calcula el ahorro por `Classification` para todo el lote y solo después crea una unidad por OTR ([createFreightUnit.java:109](../../src/org/idempiere/tms/process/createFreightUnit.java#L109), [createFreightUnit.java:149](../../src/org/idempiere/tms/process/createFreightUnit.java#L149), [createFreightUnit.java:232](../../src/org/idempiere/tms/process/createFreightUnit.java#L232)). `DD_OTRLine` guarda `DD_OTR_ID`, pero ningún `deliveryKey` calculado ([createFreightUnit.java:320](../../src/org/idempiere/tms/process/createFreightUnit.java#L320)). Por ello la reducción global actual no queda justificada por el linaje, incluso en las OTR con cabecera física resoluble. T006 deberá resolver el origen antes de agrupar y fallar cerrado cuando no exista identidad demostrable; T005 debe probar los casos anteriores.
